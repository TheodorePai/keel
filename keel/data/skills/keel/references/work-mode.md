# 默认工作模式

Keel 接入的项目按需求开展工作，按任务读取说明。这里规定工作约定的归属与维护方式；项目职责、用户目标和已有授权决定具体执行范围。

## 常驻约定与按需能力

| 位置 | 维护什么 |
|---|---|
| `AGENTS.md` | 项目职责、长期边界、必要的构建/验证入口，以及重要 skill 在什么条件下使用 |
| `.agents/skills/<name>/SKILL.md` | 可复用能力的适用条件、输出及操作流程；名称和 description 供发现能力，正文按需加载 |
| skill 的 `references/` 或项目已有资料 | 按任务读取的契约、参考与详细说明；引用权威来源，不另抄一份 |
| skill 的 `scripts/` 或项目已有工具 | 可重复、确定性的执行与校验；工具仍在原位置时直接调用 |
| Beads | 任务、验收条件、依赖与进度；知识记录按 Keel 笔记类型归位 |

一项能力是项目能做的事，不代表项目只负责这件事，也不要求所有任务先经过这套流程。已有明确项目、路径或工具时直接沿用；普通问答无需先查项目地图、登记项目或读取整套资料。

项目的授权与发布边界仍需常驻可见。skill 细化执行方式，不能扩大用户目标、已有授权或强制增加无关前置步骤。

## 维护能力时

- 遇到经实际验证、值得复用的操作流程或常见错误处理方法时，主动补充已有 skill；没有合适的再创建项目 skill。一次性小操作可直接完成，不按发生次数自动升级。
- 错误类 skill 写清触发条件、如何定位原因、怎样修复及如何确认恢复。单次事故的经过和证据留在 incident，skill 提取其中稳定、可重复执行的方法；能用代码、测试或检查防止复发的，同时落实。
- description 写清什么需求需要使用它。对容易混淆的任务说明边界；流程细节放正文，只有相关场景才读的长资料放引用文件。
- 需要可靠发现的重要能力，在 `AGENTS.md` 留一条简短的“何时使用 → skill”入口，使用指向实际文件的 Markdown 链接；无需复制流程或罗列全部已安装能力。
- 可客观校验的规则交给现有工具或脚本；项目领域校验可用 `keel.toml` 的 `verify` 接入。判断、取舍与解释保留给 Agent。
- 项目独有能力留在项目。多个项目确有相同需求时，再将通用部分合回 Keel 源码并按版本分发；个人路径、项目名册和环境事实不进入共享默认值。

## 验收与维护边界

`keel init` 默认装入本说明并补齐常驻入口；重复运行保留项目规则。`keel sync` 管理共享 skill 的版本摘要和镜像。`keel check` 检查入口是否可达、skill 格式、链接、摘要与镜像，pre-commit 对暂存内容做同样检查。

文件结构通过检查，只能证明约定可找到、结构有效。新建或实质调整能力时，按风险选取实际请求检查行为：

| 场景 | 应观察什么 |
|---|---|
| 需要该能力的请求 | 能发现 skill，并取得完成工作所需的资料与工具 |
| 相近但不需要该能力的请求 | 能直接处理，无关流程没有介入 |
| 用户已明确目标或路径 | 沿用已有上下文，避免重复定位、登记或确认 |
| 涉及权限或发布边界 | 遵守用户与项目授权，流程不会自行扩大操作范围 |

这些是行为验收的观察维度，按改动风险取样；不要求每次小改都跑完整评测。没有实际执行的场景应标明未验证。Keel 不用字数、关键词或固定章节数量断言 Agent 已正确遵循工作模式。
