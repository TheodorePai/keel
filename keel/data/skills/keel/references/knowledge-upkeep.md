# 知识收尾

任务的结果有三类去向：状态进 Beads，知识进笔记或 skill，资产进 `work/`。本说明处理第二类：工作产生或改变了以后还要用的事实时，怎样确认它已经落到下一次会话能找到的地方。

## 何时触发

- 实测得到了环境、设备、网络、账号或服务的当前状态，或推翻了已有记录。
- 改变了接口、数据格式、部署或运行方式、项目入口。
- 定位并修复了一个以后可能再遇到的问题。
- 新增、重启或退役了项目、工具、目录，导航页需要跟着变。

普通问答、没有新事实的小改动、只影响本次任务的中间结果不触发。

## 收尾前选一种去向

1. **更新已有正文**：reference、concept 就地修改，写明核实日期；已定稿的 decision、report 在末尾追加。优先改已有文档，不为同一主题另起一篇。
2. **引用权威来源**：事实归另一个项目或外部系统维护时，在本项目的入口或相关笔记里加一条指向它的链接，不抄一份。
3. **新建笔记**：没有合适位置时用 `keel new <类型> <标题>` 新建，再从导航页或相关文档链接过去。
4. **说明无需记录**：在任务关闭原因或 notes 里写一句为什么（例如“只影响本次运行”）。

可复用的操作步骤和错误处理方法归 skill，见[工作模式](work-mode.md)。

## 常见遗漏

- 结论只写在 Beads notes 里：notes 记录过程和交接，下一次会话不会把它当作当前事实来读。关闭前把结论提到正文，notes 里留链接。
- 正式证据或结论只留在 `work/.local/` 或其他可清理目录：要保留的转存为笔记附件或 `work/` 资产，再清理目录。
- 正文更新了，导航页（项目地图、README 地图、工具入口）没有更新。
- 把长期知识放进 `work/`：`work/` 放的是项目运行或交付所需的东西。

## 升级后的衔接

`keel --version` 与项目 `keel.lock` 的 `keel_version` 不同时，`keel check` 会提示。先 `keel sync` 更新共享 skill，再运行 `keel init` 迁移 Agent 入口；init 只补充缺少的入口条款，保留项目规则。之后运行 `keel check`：新版本可能检查旧布局，先修已有项目的错误，不要绕过 pre-commit。新项目直接 `keel init`，无需迁移。

## 能检查什么

`keel check` 检查链接、附件、任务 ID 和版本状态这类可以机械核对的内容。知识是否完整，需要 Agent 在收尾时判断，检查无法证明，也不要用文件数量或关键词宣称完成。行为验收时观察：下一次会话能否只靠正文和入口接续这项工作，而无需翻 Beads notes 或临时目录。
